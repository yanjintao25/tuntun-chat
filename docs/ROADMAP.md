# 后续开发建议

本文档汇总 tuntun-chat 的推荐开发路线，按优先级排列。每完成一项，请同步更新 [思路.md](./思路.md) 中的进度表。

当前基线：**待办提醒已端到端可用**；日程、每日总结仍为占位。

---

## 推荐路线总览

```mermaid
flowchart LR
    A[当前: 待办可用] --> B[P1: 生产就绪]
    B --> C[P2: 日程 + 每日总结]
    C --> D[P2: 待办增强]
    D --> E[P3: 扩展能力]
```




| 优先级    | 目标       | 建议工期  |
| ------ | -------- | ----- |
| **P1** | 生产可用、可运维 | 1–2 天 |
| **P2** | 补齐核心三能力  | 3–5 天 |
| **P2** | 待办体验增强   | 2–3 天 |
| **P3** | 新能力与架构演进 | 按需    |

## P1 — 生产就绪（建议优先）

上线到云服务器、长期跑定时任务前，建议先完成以下项。

### 1. `/admin` 鉴权


| 项        | 说明                                                                     |
| -------- | ---------------------------------------------------------------------- |
| **为什么**  | 当前 `GET/PUT /admin/config` 无鉴权，公网暴露有风险                                 |
| **怎么做**  | 环境变量 `ADMIN_API_KEY`；中间件校验 `Authorization: Bearer <key>` 或 `X-API-Key` |
| **改动文件** | `src/routes/admin-config.ts`，新建 `src/middleware/admin-auth.ts`         |
| **验收**   | 无 Key 返回 401；正确 Key 可读写配置                                              |


### 2. 日志与可观测性


| 项        | 说明                                                               |
| -------- | ---------------------------------------------------------------- |
| **为什么**  | scheduler 推送失败、LLM 超时等需便于排查                                      |
| **怎么做**  | 统一日志前缀（已有 `[scheduler]` 等）；关键路径记录 `openId`、`todoId`、错误栈；可选接入文件日志 |
| **改动文件** | `scheduler/reminder.ts`、`todo/service.ts`、`llm/openai.ts`        |
| **验收**   | 推送失败、抽取失败在日志中可定位到具体待办                                            |


### 3. 基础自动化测试


| 项        | 说明                                                           |
| -------- | ------------------------------------------------------------ |
| **为什么**  | `remind_at` 计算、store CRUD、扫描 SQL 是稳定核心，适合单测                  |
| **怎么做**  | 引入 `vitest` 或 `node:test`；内存 SQLite 或临时文件测 store             |
| **优先覆盖** | `computeRemindAt`、create/list/complete、`findDueReminders` 条件 |
| **验收**   | `npm test` 在 CI 本地可通过                                        |


### 4. 部署清单核对


| 项       | 说明                                                      |
| ------- | ------------------------------------------------------- |
| **参考**  | [DEPLOY.md](./DEPLOY.md)                                |
| **核对项** | 长连接/Webhook 二选一；`im:message` 发送权限；PM2 常驻；scheduler 启动日志 |

## P2 — 补齐核心能力

### 5. 日程管理（接入飞书日历）


| 项        | 说明                                                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **参考**   | [SCHEDULE-VS-TODO.md](./SCHEDULE-VS-TODO.md)、飞书 [日历事件 API](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/create) |
| **怎么做**  | 仿照 `todo/` 结构：`schedule/extract.ts`、`schedule/service.ts`；LLM 抽标题/开始/结束/全天；调 `calendar_event` 创建                                          |
| **改动文件** | `features/schedule.ts`、`feishu/client.ts`（日历 API 封装）、`config/store.ts`（`defaultCalendarId`）                                               |
| **权限**   | 申请 `calendar:calendar` 等                                                                                                                  |
| **验收**   | 「明天下午 3 点开会」在飞书日历可见                                                                                                                       |


### 6. 每日总结


| 项        | 说明                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| **怎么做**  | `scheduler/daily-summary.ts`：在 `summaryTime`（默认 18:00）触发；拉取当日 `todos`（+ 日后日程）；LLM 生成总结；`sendTextToChat` 推送 |
| **数据**   | 可先读自建 `todos`；日程接入后一并纳入                                                                                    |
| **可选表**  | `daily_summary_logs`（防重复推送），见 [DATABASE.md](./DATABASE.md) 第三节                                             |
| **改动文件** | `features/daily-summary.ts`、`scheduler/`、`config/store.ts`                                                 |
| **验收**   | 到点收到「今日总结」；用户主动说「每日总结」也能触发                                                                                 |

## P2 — 待办体验增强

在 MVP 跑稳后，按价值排序：

### 7. 管理 API：后台创建/查询待办


| 项        | 说明                                                             |
| -------- | -------------------------------------------------------------- |
| **接口建议** | `GET /admin/todos?openId=`、`POST /admin/todos`                 |
| **改动文件** | `src/routes/admin-todos.ts`、`todo/service.ts`（`source: admin`） |
| **依赖**   | P1 鉴权                                                          |


### 8. 每日未完成待办汇总


| 项        | 说明                                                           |
| -------- | ------------------------------------------------------------ |
| **怎么做**  | 早 9 点 cron；`listPendingTodosInRange` 或 `due_at < today`；推送清单 |
| **改动文件** | `scheduler/reminder.ts` 或新建 `scheduler/daily-digest.ts`      |


### 9. 主动追问完成情况


| 项       | 说明                                              |
| ------- | ----------------------------------------------- |
| **怎么做** | 傍晚对「今日到期仍 pending」发「是否已完成？」；用户回复走 `complete` 意图 |
| **注意**  | 避免与到期提醒重复轰炸，可配置开关                               |


### 10. 列表序号与完成意图对齐


| 项       | 说明                                                           |
| ------- | ------------------------------------------------------------ |
| **问题**  | 列表展示 1、2、3，但 `complete` 按 DB `id` 匹配，用户说「完成第 1 条」可能对错        |
| **怎么做** | `extract` 返回列表序号；`service` 按 `listPendingTodos` 下标解析，而非 `id` |


### 11. 飞书 Task API 同步（可选）


| 项       | 说明                                     |
| ------- | -------------------------------------- |
| **怎么做** | `todos` 表增 `feishu_task_id`；创建/完成时双向同步 |
| **何时做** | 需要与飞书客户端待办互通时再做；自建表已够用                 |

## P2 — 管理与体验

### 12. 管理后台 Web 界面


| 项      | 说明                                      |
| ------ | --------------------------------------- |
| **范围** | 功能开关、待办列表、手动创建/取消                       |
| **技术** | 简单静态页 + fetch `/admin/`*，或 Vue/React 单页 |
| **依赖** | P1 鉴权、可选 #7 待办 API                      |


### 13. 对话体验


| 项          | 说明                                                             |
| ---------- | -------------------------------------------------------------- |
| **多轮上下文**  | `runner` 维护最近 N 轮 history（按 `openId` 内存或 Redis）                |
| **意图识别统一** | 日程/总结也改为 JSON 抽取，减少 `[tag]` 误触发                                |
| **配置扩展**   | `todo.dueReminderEnabled`、`defaultDueHour` 等写入 `FeatureConfig` |

## P3 — 扩展能力（长期）

来自 [思路.md](./思路.md)，按需迭代，每项独立成 `features/`* + `runner` 分发：


| 方向   | 示例               | 集成方式                        |
| ---- | ---------------- | --------------------------- |
| 生活信息 | 天气、新闻、股票         | 第三方 API + LLM 整理回复          |
| 内容推送 | 名言、古诗词、健康提示      | scheduler 定时 + 配置订阅         |
| 任务流  | 多模型、多 handler 编排 | 新建 `pipeline/` 或增强 `runner` |


---

## 建议的下一步（若只选一件事）

**优先做 P1 的 `/admin` 鉴权**，改动小、收益高，且是管理 API / 后台 UI 的前置条件。

若更关注产品完整度，**接着做 P2 的每日总结**——可直接复用已有 `todos` 数据与 `scheduler`，比日程 API 权限申请更快见效。
